# Concurrent dispatch resource audit

The [CLI dispatcher](../../src/cli/program.ts#L2679) allocates a Git branch and worktree, writes a SpawnRecord, builds an image, starts a container, and saves its logs. The [Hatchery handoff](../../src/hatchery/spawn-handoff.ts#L1255) allocates a Castra steward first, then uses its worktree for the shared Spawn pipeline. Ownership is scoped to the namespace in each row. A successful allocation in one namespace confers no rights in another.

## Shared Spawn resources

| Resource and namespace | Allocation and conflict handling | Cleanup ownership |
| --- | --- | --- |
| Spawn ID candidate | Both paths use the UTC date and 24 random bits. The CLI reserves its branch in the source repository, retrying if a ref already exists or Git rejects creation. Hatchery accepts an explicit branch or derives one from the candidate, then separately asks Castra to launch it. Neither path makes a single reservation spanning the shared home, repositories and Docker daemon. [ID and worktree allocation](../../src/brood/worktree.ts#L39), [Hatchery allocation](../../src/hatchery/spawn-handoff.ts#L1255) | Each subsystem has its own rollback, described below. **CD-01** |
| CLI branch ref and linked worktree | Git owns the ref in the source repository. The CLI pre-check is advisory and successful `git branch` is the reservation. The worktree lives under the source repository's parent at `worktrees/march/<id>`, so sibling repositories can share the directory namespace. A path already present at the check is preserved and only the newly created branch is deleted. If the path appears after the check and Git refuses the add, rollback still receives the path. [Git allocation](../../src/brood/worktree.ts#L151) | Exact-path removal followed by deletion of the named ref. The filesystem fallback checks for a linked-worktree marker, which does not prove the caller owns that registration. **CD-02**. [Worktree rollback](../../src/brood/worktree.ts#L276) |
| Build context and prompt staging under the host temp directory | Each call owns a directory reserved by `mkdtempSync`. Snapshot copies tracked files into its context and the generated Dockerfile lives there. Prompt staging (and optional telemetry emitter staging) has its own exclusive directory. [Build context](../../src/spawn/snapshot.ts#L246), [Dockerfile](../../src/spawn/snapshot-build.ts#L70), [Prompt and emitter staging](../../src/spawn/container-launch.ts#L423) | Snapshot construction cleans its own directory on error and both dispatchers clean the returned context in a build `finally`. Staging helpers remove their own directories after copy. [CLI build](../../src/cli/program.ts#L2813), [Hatchery build](../../src/hatchery/spawn-handoff.ts#L1389) |
| Image tag on the selected Docker daemon | The common build helper tags the image `march-spawn-<id>`. The build can move a tag already pointing at another image. The record's `imageId` stores the tag. [Image build](../../src/spawn/snapshot-build.ts#L135) | Failed build cleanup removes by tag, as do CLI build/launch rollback and Hatchery non-parking rollback. Hatchery can remove the tag even when it failed before building. Successful dispatch retains its image. **CD-03**. [Image removal](../../src/spawn/snapshot-build.ts#L193), [Hatchery rollback](../../src/hatchery/spawn-handoff.ts#L1704) |
| Container name and ID on the same daemon | Docker exclusively allocates the name `march-spawn-<id>`. A duplicate create is rejected. Successful create returns Docker's immutable ID, which dispatch uses for prompt copy, start, wait, and logs. [Create and copy](../../src/spawn/container-launch.ts#L319) | Timeout removes by returned ID. Failed create itself removes by derived name, and CLI launch rollback repeats that name-based cleanup. Hatchery gates its outer container rollback on a returned ID but still removes by name. Successful dispatch retains the stopped container. **CD-04**. [Wait and removal](../../src/spawn/container-launch.ts#L490), [CLI launch rollback](../../src/cli/program.ts#L2903), [Hatchery rollback](../../src/hatchery/spawn-handoff.ts#L1704) |
| SpawnRecord under `<home>/.march/spawns/<id>.json` | Exclusive `wx` creation rejects a claimed path. A read concurrent with the initial write can see incomplete JSON. Updates read the old JSON, write a randomly named sibling, and rename over the target. Readers of a successful rename see whole old or new JSON. Random suffixes reduce temporary-name collisions but those opens lack exclusivity. State checks read the record before rename and do not serialize competing updates. [Creation and update helpers](../../src/brood/spawn-record.ts#L126) | CLI initialization rollback removes by ID even when exclusive creation rejected that ID. Hatchery's general catch attempts to mark the record failed even if it never acquired it. CLI later failures attempt to keep a failed record, and successful records remain readable. **CD-05**, **CD-06**. [CLI record rollback](../../src/cli/program.ts#L2783), [Hatchery failure handler](../../src/hatchery/spawn-handoff.ts#L1680) |
| Output on the dispatch filesystem | CLI writes `<home>/.march/spawns/<id>.output.log` by truncating write after reading logs by container ID. Hatchery writes `spawn-output.log`, `patch.diff`, `manager-prompt.md` and metadata under `<home>/.march/logs/hatchery-spawns/<id>/`, and can write a failure manifest under `<home>/.march/hatchery/parked/<id>.json`. Each path inherits ID ownership and has no independent exclusive publication. [CLI output](../../src/cli/program.ts#L2936), [Hatchery artifacts](../../src/hatchery/spawn-handoff.ts#L705), [Parking manifest](../../src/hatchery/spawn-handoff.ts#L226) | Dispatch leaves written logs and artifacts for inspection, including on failure. A competing write at the same path can overwrite them. **CD-07**. |

## Hatchery and Brood

| Resource and namespace | Allocation and conflict handling | Cleanup ownership |
| --- | --- | --- |
| Hatchery job ID in the service process | The [job store](../../src/hatchery/service/jobs.ts#L98) uses a UUID to key a pending job. That ID is for polling and does not reserve a Spawn ID, slice, or branch. The job is marked terminal in the same map. | Job state is in memory. The handoff worker owns infrastructure rollback independently. |
| Steward session, ref and worktree on the Castra host | Hatchery sends repository, profile, branch, title, group and spawn/slice metadata to Castra. The [Castra adapter](../../src/castra/adapter.ts#L448) asks agent-deck to create the worktree and associate a session. The default branch derives from the Spawn ID, an explicit branch can repeat, and the worktree basename flattens slashes to dashes. Castra looks up the resulting session by that basename and validates it before returning. A matching basename alone cannot prove ownership when names alias. Hatchery pins and applies to the returned worktree. [Steward launch](../../src/hatchery/spawn-handoff.ts#L769), [Patch apply](../../src/hatchery/spawn-handoff.ts#L950) | Failed handoff removes the returned session by profile and ID with worktree cleanup, then removes the exact remaining branch/path, or parks the worktree and ref before removing the session. On duplicate ref at launch, self-heal checks ancestry/PR safety and resolves the exact ref/path. An active steward can still own a branch at the default tip. Success leaves the steward for lifecycle teardown. **CD-08**. [Self-heal](../../src/hatchery/spawn-handoff.ts#L283), [Handoff rollback](../../src/hatchery/spawn-handoff.ts#L1704) |
| Castra launch sidecar on the steward host | The report hook's context is written under the Castra steward skills directory. The filename includes a hash prefix of the resolved worktree path. Separate worktree paths generally separate sidecars, while launches at the same path overwrite the same file. In-memory correlation uses the returned session ID. [Sidecar key and write](../../src/castra/steward-skills.ts#L88), [Session correlation](../../src/castra/adapter.ts#L622) | A later launch prunes sidecars older than 14 days, without checking whether the session is still live. The sidecar is written only at launch and the hook reads it without refreshing it, so a steward active for more than 14 days loses its context and may send no report. The [TTL](../../src/castra/steward-skills.ts#L113) assumes no steward lives that long. The stat and unlink are separate, so a stale file can also be replaced between the two calls. **CD-11**. |
| Default tracking ref in the manager repository | Hatchery fetches the shared default tracking ref using Git's ref update and locking. It resolves a single commit ID before the ancestry check and resets the manager worktree to that ID. A later fetch by another job can move the tracking ref without changing the sampled commit. [Base pin](../../src/hatchery/spawn-handoff.ts#L1198) | Rollback manages the steward worktree and branch. The repository keeps the shared tracking ref. |
| Brood filesystem index under the selected home | The index lists JSON files, retries one failed parse when listing, and reads by ID for lookup. It allocates and writes nothing. A concurrent initial write can be briefly missing from a listing if both reads fail; a rename-based update offers a whole record per read, with no consistent snapshot across a whole listing. [Index reader](../../src/brood/spawn-index.ts) | The reader removes nothing. |
| Brood lifecycle registry in the service database | With Brood configured, Hatchery registers a spawn and its steward at launch and enriches those rows after success. The registry keys by ID, merges defined fields, preserves kind and upserts. It allocates no branch, worktree or SpawnRecord path. A colliding or stale registration can still write another attempt's lifecycle fields. [Registration](../../src/hatchery/service/brood-registration.ts), [Registry merge](../../src/brood/service/store.ts#L250) | Failed handoff leaves launch rows available to Brood for reconciliation. Brood teardown acts on the recorded session and artifacts, so wrong ownership in a row can affect teardown. **CD-09**. [Teardown](../../src/brood/service/teardown.ts#L132) |
| Herald slice projection | After steward launch, Hatchery publishes the slice/session/spawn correlation if Herald and a slice ID are configured. This is a best-effort observation keyed by slice. Concurrent attempts for one slice can publish competing correlations. [Publication](../../src/hatchery/spawn-handoff.ts#L1378) | Publication has no compensating deletion during handoff rollback. **CD-10**. |

## Follow-up PR tracking

Each open entry records an ownership check a separate fix PR must establish. No fix PR exists yet, and this audit ships none. The linked issue tracks each fix until its PR is opened, and that PR closes the issue. The CLI scenario keeps its isolation assertions and uses the ordinary success path.

| ID | Open follow-up PR scope | Failing ownership check | Tracking |
| --- | --- | --- | --- |
| CD-01 | Reserve dispatch identity across workers sharing a home or daemon before allocating ID-derived resources. | A Git ref in one repository does not establish ownership of the same ID in another repository, home, or daemon. Hatchery has no equivalent ID reservation. | [#686](https://github.com/Balexda/March/issues/686) |
| CD-02 | Bind worktree failure rollback to the creating Git registration. | After the existence check, another linked worktree can occupy the path. The fallback accepts a linked-worktree marker without matching it to the new ref and repository. | [#687](https://github.com/Balexda/March/issues/687) |
| CD-03 | Refuse to replace a claimed Docker tag and roll back a verified build. | Build and rollback use a tag without verifying that it belongs to this attempt. | [#688](https://github.com/Balexda/March/issues/688) |
| CD-04 | Remove containers only using the resource ID acquired by the attempt. | Docker rejects a duplicate name but failed-create cleanup can remove the existing container by that name. | [#689](https://github.com/Balexda/March/issues/689) |
| CD-05 | Gate record deletion and failure transitions on successful ownership acquisition. | `EEXIST` preserves the file at creation, then the CLI catch can delete it or the Hatchery catch can mark it failed. | [#690](https://github.com/Balexda/March/issues/690) |
| CD-06 | Publish initial records as whole files with exclusive acquisition and serialize updates for each owner. | Initial create can expose partial JSON. Sibling staging is not exclusive, and an update can overwrite a competing transition or replace a record recreated since its read. | [#691](https://github.com/Balexda/March/issues/691) |
| CD-07 | Publish output and forensic files under verified attempt ownership. | A truncating write accepts a pre-existing output or manifest path without checking who created it. | [#692](https://github.com/Balexda/March/issues/692) |
| CD-08 | Bind Castra attach and branch self-heal to a specific live launch owner. | A flattened basename is insufficient to establish session identity. Ancestry/PR safety does not establish that an existing branch and worktree have no active steward. | [#693](https://github.com/Balexda/March/issues/693) |
| CD-09 | Reject conflicting or stale Brood registrations with an attempt identity check. | Upsert merges by ID without verifying that new artifact pointers originate from the same attempt. | [#694](https://github.com/Balexda/March/issues/694) |
| CD-10 | Require attempt ownership when updating the Herald slice correlation. | Publishing the slice ID and resource pointers does not establish that the dispatch is the current attempt for that slice. | [#695](https://github.com/Balexda/March/issues/695) |
| CD-11 | Bind steward hook context to the launch, expire it by session liveness rather than age alone, and guard expiration against replacement. | The sidecar keys on path without validating the launch identity. Age-based unlink does not check that the session has ended, so a live steward older than the 14-day TTL loses its sidecar. Unlink also does not verify the file is still the one whose mtime was checked. | [#696](https://github.com/Balexda/March/issues/696) |

## CI evidence

The [cassette scenario](../../src/spawn/concurrent-dispatch.integration.test.ts) runs two `march spawn dispatch` processes against one temporary repository, home and real Docker daemon. A fixture Claude executable replays a response selected by the prompt and verifies the tracked seed file reached its container. Both containers must be running, with their CLI processes still in flight, before the test releases either response. The scenario checks two successful exits, distinct refs, worktree paths, image tags, container names and IDs, and record paths. It cross-checks those resources against Git, Docker and both Brood index lookups, and matches each output file and CLI response to its prompt. It also checks that snapshot and prompt staging directories have been cleaned.

The Docker fixture requires a Linux daemon that can run a privileged nested daemon. The existing cassette CI job runs the scenario even if Docker is missing, which surfaces the missing prerequisite as a failure. Local runs without Docker skip it.

The test exercises overlapping allocation and normal record transitions with independent IDs. Forced reuse, contested rollback, reads during initial record writes, the Castra handoff, and Brood registration are source-audited. Deadlines bound the replay and host calls. The fixture's private daemon and temp root delimit cleanup on both success and failure, following March's [vision](../../docs/vision.md) and [operating philosophy](../../docs/operating-philosophy.md).
